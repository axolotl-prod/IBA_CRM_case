# База данных FinanceCRM

Проект использует локальную SQLite-базу `data/crm.sqlite`. Она создаётся автоматически при первом серверном запросе. Схема находится в [`database/schema.sql`](database/schema.sql), серверный слой доступа — в [`src/server/database.ts`](src/server/database.ts).

## Что хранится в базе

Схема повторяет текущие функции CRM:

- авторизация руководителя и менеджеров;
- канбан заявок с назначенным менеджером и статусом воронки;
- оплаты, выручка, чистая сумма, долг и график рассрочки;
- базовые параметры зарплаты и бонусов сотрудника;
- переопределение планов и коэффициентов по месяцам;
- автоматическое создание оплаты при переводе лида в статус `paid`.
- очередь Telegram-уведомлений о новых заявках из Google Sheets.
- PDF-счета, их версии, статусы отправки и журнал действий.

Пользовательские данные больше не хранятся в `localStorage`. В браузере остаётся только ID текущего пользователя для восстановления интерфейса. Пароли сохраняются в виде `scrypt`-хеша с индивидуальной солью.

## Псевдографическая ER-схема

```text
┌──────────────────────────── USERS ────────────────────────────┐
│ PK id                                                         │
│ UQ login                password_hash + password_salt          │
│    name                 role: admin | manager                  │
│    salary_kopecks       bonus_rate                             │
│    min/target/max_plan_kopecks                                 │
│    min/target/max_multiplier                                  │
└───────────────┬───────────────────────┬───────────────────────┘
                │ 1                     │ 1
                │                       │
                │ N                     │ N
┌───────────────▼──────────────┐  ┌─────▼────────────────────────┐
│       MONTHLY_PLANS          │  │             LEADS            │
│ PK,FK user_id                │  │ PK id                         │
│ PK    month (YYYY-MM)        │  │ FK manager_id ────────────────┼──┐
│       salary_kopecks         │  │    lead_date, name            │  │
│       bonus_rate             │  │    phone, telegram, income    │  │
│       min/target/max_plan    │  │    request, comment            │  │
│       min/target/max_mult.   │  │    status, raw_status, tariff │  │
└──────────────────────────────┘  │    amount/net_amount_kopecks  │  │
                                  │    payment_method, paid_at     │  │
                                  └──────────┬──────────┬───────────────┘  │
                                             │ 1        │ 1                 │
                                             │          │                   │
                                             │ 0..N     │ 0..1              │
                           ┌─────────────────▼────┐ ┌───▼────────────────┐  │
                           │      PAYMENTS        │ │ TELEGRAM_NOTIFICATIONS│ │
                           │ PK id                │ │ PK id                 │ │
                           │ UQ order_no          │ │ UQ,FK lead_id         │ │
                           │ FK lead_id           │ │ status: pending|sent  │ │
                           │ FK manager_id ───────┼─┼───────────────────────┼─┘
                           │ revenue/net/debt     │ │ attempts, last_error  │
                           │ paid_at, schedule    │ │ created_at, sent_at   │
                           └──────────────────────┘ └───────────────────────┘
```

Связи:

- `users 1 → N leads`: менеджер ведёт много заявок;
- `users 1 → N payments`: менеджеру относится много оплат;
- `users 1 → N monthly_plans`: для сотрудника можно сохранить отдельный план на каждый месяц;
- `leads 1 → 0..N payments`: оплата может быть создана из лида; ручная оплата может не иметь `lead_id`.
- `leads 1 → 0..1 telegram_notifications`: для новой заявки Google Sheets создаётся одно уведомление; повторный импорт не создаёт дубликат.

При удалении сотрудника его помесячные планы удаляются (`CASCADE`), а лиды и оплаты сохраняются, но их `manager_id` становится `NULL` (`SET NULL`). Это не уничтожает историю продаж.

## Таблицы

### `users`

Сотрудники, роли, учётные данные и базовые параметры мотивации. `login` уникален без учёта регистра. Денежные значения хранятся в копейках, чтобы избежать ошибок двоичной арифметики `REAL`.

### `monthly_plans`

Снимок всех параметров мотивации для пары `(user_id, month)`. Составной первичный ключ запрещает два плана одному сотруднику на один месяц. Если записи нет, приложение использует базовые значения из `users`.

### `leads`

Карточки канбана. `status` ограничен значениями `new`, `work`, `kp`, `paid`, `closed`. Текстовый `raw_status` оставлен отдельно для исходных импортированных данных. Поля `source` и `external_id` отличают ручные заявки от Google Sheets и предотвращают повторную загрузку одной строки.

### `payments`

Фактические оплаты. `order_no` — уникальный последовательный номер. `lead_id` допускает `NULL`, потому что текущий интерфейс позволяет внести оплату вручную. Поля `revenue_kopecks`, `net_kopecks` и `debt_kopecks` разделяют оборот, чистый доход и остаток долга.

### `telegram_notifications`

Надёжная очередь Telegram-сообщений. Запись создаётся в той же транзакции, что и новая заявка Google Sheets. После успешной отправки статус меняется с `pending` на `sent`; при ошибке сохраняются число попыток и причина, а сообщение остаётся в очереди для следующей синхронизации. Уникальный `lead_id` защищает от повторных уведомлений.

### Telegram-чаты

```text
┌───────────┐    ┌─────────────────────┐    ┌───────────────────┐
│   LEADS   │1──1│ LEAD_TELEGRAM_LINKS │N──1│ TELEGRAM_CONTACTS │
└───────────┘    │ start_token         │    └─────────┬─────────┘
                 └─────────────────────┘              │1
                                                      │
                                                      │1
                                            ┌─────────▼─────────┐
┌───────────┐                             N │  TELEGRAM_CHATS   │
│   USERS   │1──────────────────────────────│ manager_id        │
└───────────┘                               └─────────┬─────────┘
                                                      │1
                                                      │
                                                      │N
                                           ┌──────────▼──────────┐
                                           │ TELEGRAM_MESSAGES  │
                                           │ text, file, status │
                                           └─────────────────────┘
```

- `telegram_contacts` хранит постоянные Telegram user ID и chat ID клиента;
- `telegram_chats` хранит ответственного менеджера, последнее сообщение и непрочитанные;
- `lead_telegram_links` связывает заявки с контактом через уникальный `/start`-токен;
- `telegram_messages` содержит единую историю входящих, исходящих и системных сообщений вместе со статусами и метаданными файлов;
- `telegram_state` хранит безопасный offset long polling и техническое состояние интеграции.

## Счета клиентам

```text
┌──────────────────┐       1        N ┌──────────────────────────┐
│      LEADS       │─────────────────►│         INVOICES         │
│ PK id            │                  │ PK id                    │
│    name, phone   │                  │ UQ invoice_no            │
│    telegram      │                  │ FK lead_id, manager_id   │
└──────────────────┘                  │ amount, quantity, VAT    │
                                      │ company/customer snapshot│
┌──────────────────┐       1        N │ status, current_version  │
│      USERS       │─────────────────►│ created_at, sent_at      │
└──────────────────┘                  └────────────┬─────────────┘
                                                  │ 1
                              ┌───────────────────┴───────────────────┐
                              │ N                                   N │
                    ┌─────────▼──────────┐              ┌────────────▼─────────┐
                    │ INVOICE_VERSIONS   │              │    INVOICE_EVENTS    │
                    │ version, pdf_path  │              │ event_type, user_id  │
                    │ sha256, file_size  │              │ details, created_at  │
                    └────────────────────┘              └──────────────────────┘

┌────────────────────────┐       ┌───────────────────────────────┐
│    COMPANY_SETTINGS    │       │       INVOICE_COUNTERS        │
│ реквизиты поставщика   │       │ PK year, last_number         │
│ is_test                │       │ СЧ-ГГГГ-00001                │
└────────────────────────┘       └───────────────────────────────┘

INVOICES 1 ── 0..N TELEGRAM_MESSAGES (invoice_id)
```

- `company_settings` хранит реквизиты поставщика. Сейчас при первом запуске создаётся тестовая компания со случайными вымышленными реквизитами и признаком `is_test = 1`.
- `invoices` хранит номер, сумму, описание, НДС, срок оплаты, статус и неизменяемые снимки реквизитов компании и клиента на момент выставления.
- `invoice_versions` связывает счёт с сохранённым PDF, размером и SHA-256. Это позволяет в дальнейшем добавлять новые редакции, не теряя старые документы.
- `invoice_events` — аудит создания, сохранения, успешной отправки и ошибок.
- `invoice_counters` выдаёт последовательные номера отдельно по каждому году.
- `telegram_messages.invoice_id` связывает отправленный документ с единым Telegram-диалогом клиента.

Предпросмотр создаётся во временной системной папке `salesspark-invoice-previews` и после скачивания удаляется. Подтверждённые файлы находятся в `data/invoices/<год>/`. Каталог `data/invoices` исключён из Git, но его нужно включать в резервные копии вместе с SQLite.

Жизненный цикл счёта:

```text
Форма менеджера
      │
      ▼
PDF-предпросмотр ──► исправление формы ──► новый предпросмотр
      │ всё проверено
      ▼
Сохранение в карточку (`saved`) ──► отправка PDF в Telegram (`sent`)
      │                                      │
      └──────── PDF + аудит в CRM ───────────┘
```

Кнопка сохранения становится доступной только для актуального предпросмотра. Любое изменение суммы, описания или других полей требует сформировать PDF заново. Отправить можно только уже сохранённый счёт, а клиент должен предварительно подключить Telegram-бота через `/start`.

PDF формируется локально установленным Microsoft Edge. Если Edge установлен нестандартно, путь задаётся переменной `EDGE_PATH` в `.env`.

## Инициализация и источник данных

Первичное наполнение лидов и оплат выполнено из файла `../Запуск январь-февраль.xlsx`. Новые лиды также автоматически поступают из подключённой Google Sheets. Данные из `src/lib/seed.json` не используются.

Для повторной полной загрузки используется команда:

```powershell
npm run db:import:excel
```

Импорт выполняет следующие действия:

1. Читает напрямую XML-структуру книги XLSX без промежуточного копирования данных из приложения.
2. Берёт лиды с листов `Лиды Паша` и `Лиды Алина`, оплаты — с листа `Оплаты`. Лист `дашборд` пропускается, потому что содержит вычисляемые итоги.
3. Исключает строку-разделитель `С ВЕБА`, итоговую строку оплат и пустые форматированные строки.
4. Полностью очищает `payments`, `leads`, `monthly_plans` и `users` внутри одной транзакции.
5. Восстанавливает три необходимые системе учётные записи и загружает 174 лида и 95 оплат из Excel.
6. Преобразует серийные даты Excel в ISO `YYYY-MM-DD`, суммы — в целые копейки, `ОП` и `ОП и Вася` — в менеджера `Вася`.
7. Приводит варианты написания рассрочки к `рассрочка`, удаляет лишние пробелы и сопоставляет текстовые статусы с колонками канбана.
8. Связывает оплату с лидом только при единственном совпадении имени и менеджера; неоднозначные совпадения остаются без `lead_id`.

Системные пользователи не считаются импортированными бизнес-данными: они нужны для входа и внешних ключей. При обычном запуске пустой базы создаются только эти пользователи; лиды и оплаты загружаются исключительно указанной командой из Excel.

Путь можно изменить переменной окружения `CRM_DATABASE_PATH`. Например, в PowerShell:

```powershell
$env:CRM_DATABASE_PATH = "D:\finance-crm\crm.sqlite"
npm run dev
```

## Индексы и запросы интерфейса

- `idx_leads_status` ускоряет построение колонок канбана;
- `idx_leads_manager_date` ускоряет выборку заявок менеджера;
- `idx_payments_manager_date` обслуживает дашборд и месячные отчёты;
- `idx_payments_lead` ускоряет поиск оплат конкретного лида;
- `idx_monthly_plans_month` ускоряет просмотр планов за месяц.

## Эксплуатационные ограничения

SQLite подходит для текущего односерверного CRM-приложения и небольшой команды. Файл базы должен лежать на постоянном локальном диске; поэтому production-сборка настроена на Nitro `node-server`, а не на Cloudflare Workers. Для нескольких экземпляров приложения или интенсивных параллельных записей следующий логичный шаг — PostgreSQL.

Файлы `crm.sqlite`, `crm.sqlite-wal` и `crm.sqlite-shm` исключены из Git. Для резервного копирования следует использовать SQLite backup API или команду `VACUUM INTO`, а не копировать активный файл без учёта WAL.
